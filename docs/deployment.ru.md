# Размещение и обслуживание

[README](../README.ru.md) · [English](deployment.md) · [Конфигурация](configuration.ru.md)

## Публичное размещение

Файл `docker-compose.yml` собирает frontend и Python backend в один контейнер и привязывает приложение к `127.0.0.1:8080`. Uvicorn обслуживает **HTTP**. Для публичного размещения HTTPS обеспечивает reverse proxy на том же сервере. Приложение должно находиться в корне отдельного домена: префиксы вроде `/spotify/` не поддерживаются.

```text
Браузер / OBS -> https://music.example.com:443 -> Caddy или nginx
                                            -> http://127.0.0.1:8080 -> приложение
```

Нужны сервер с Docker и Compose, домен с DNS-записями A/AAAA на этот сервер и доступные для прокси входящие TCP-порты 80 и 443. Публикуйте AAAA только при работающем IPv6. Оставьте порт 8080 привязанным к loopback, как в исходном Compose-файле. Репозиторий самостоятельно не настраивает DNS, прокси и сертификаты.

### Настройка Spotify и запуск приложения

Создайте собственный `.env` по [быстрому старту](../README.ru.md#быстрый-старт) и укажите Client ID своего Spotify-приложения. Значения в примерах — заглушки, общих ключей проекта нет. Telegram и текст песен можно подключить после проверки основного развёртывания.

Добавьте публичный callback в Spotify Developer Dashboard и укажите тот же адрес в `.env`:

```dotenv
SPOTIFY_REDIRECT_URI=https://music.example.com/auth/callback
```

```sh
docker compose up --build -d
curl --fail http://127.0.0.1:8080/healthz
```

После изменения существующего `.env` выполните `docker compose up -d --force-recreate`. Команда `docker compose restart` не обновляет переменные окружения контейнера.

Настройте один из прокси ниже, затем откройте `https://music.example.com/setup` и подключите Spotify. Весь вход выполняйте через один HTTPS-домен. Приложение выставляет OAuth cookie флаг `Secure` по `SPOTIFY_REDIRECT_URI`, а не по заголовкам прокси. Внутреннее соединение прокси с приложением может оставаться HTTP. Если начать вход через loopback HTTP, а callback направить на публичный HTTPS-домен, браузер не передаст cookie.

Spotify требует HTTPS для удалённых callback. Локальный HTTP разрешён только с явным loopback IP, например `127.0.0.1` или `[::1]`, но не `localhost`. См. [правила Spotify](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri).

### Caddy на сервере: автоматические сертификаты

Возьмите [пример Caddyfile](examples/Caddyfile), заменив `music.example.com` своим доменом:

```caddyfile
music.example.com {
    reverse_proxy 127.0.0.1:8080 {
        flush_interval -1
    }
}
```

Для стандартной службы Caddy в Linux сохраните конфигурацию в `/etc/caddy/Caddyfile`. Если сервер уже обслуживает другие сайты, добавьте блок в существующий файл. Проверьте и примените:

```sh
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
```

Caddy должен быть установлен, а его служба — запущена. При корректном DNS и доступных портах проверки домена Caddy получает и обновляет публичный сертификат, а также перенаправляет HTTP на HTTPS. Сохраняйте каталог данных Caddy, чтобы сертификаты переживали перезапуски. Access logs в примере не включены. Подробнее: [автоматический HTTPS](https://caddyserver.com/docs/automatic-https), [передача потоков](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).

### nginx на сервере: готовые сертификаты

Добавьте [полный пример nginx](examples/nginx.conf) в контекст `http`: например, сохраните в `/etc/nginx/sites-available/spotify-now-playing` и создайте ссылку в `sites-enabled` на Debian/Ubuntu. Замените все домены и оба пути к сертификатам.

**Получите действующий сертификат до включения конфигурации.** Этот пример не получает и не обновляет сертификаты. Используйте ACME-клиент (например Certbot) или средства хостинга, настройте продление и перезагрузку nginx после него. Для standalone-проверки ACME нужен свободный порт 80 во время выпуска; для webroot-проверки нужен отдельный location. HTTP-блок из примера только перенаправляет запросы и не раздаёт файлы webroot-проверки.

Основные параметры проксирования из полного примера:

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header Connection "";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 90s;
    gzip off;
}
```

После установки полной конфигурации проверьте и примените её:

```sh
sudo nginx -t
sudo systemctl reload nginx
```

Команды рассчитаны на запущенную службу nginx в Linux. Полный пример перенаправляет HTTP на HTTPS и отключает access logs этого виртуального хоста, чтобы query string callback не попадали в журнал. См. [документацию nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html).

### Поток обновлений, iframe и прокси в контейнере

`/api/v1/spotify/public/stream` использует Server-Sent Events (SSE), а не WebSocket. Сразу приходит снимок состояния, при отсутствии обновлений отправляются keep-alive комментарии (тайм-аут 20 секунд). На дополнительных прокси/CDN отключите для этого пути буферизацию, кэширование и преобразование ответа; тайм-аут простоя должен превышать 20 секунд. Для встраивания `/widget` на другом сайте не добавляйте глобальные `X-Frame-Options: DENY` / `SAMEORIGIN` и запрещающий `frame-ancestors`. Страницы настройки и OAuth запрещают встраивание сами. На HTTPS-сайте используйте HTTPS-адрес виджета, иначе браузер заблокирует mixed content.

Оба готовых примера рассчитаны на прокси, установленный **на хосте**. Если прокси работает в контейнере, `127.0.0.1` указывает на сам контейнер прокси. Подключите оба сервиса к одной Docker-сети и замените upstream на `spotify:8080` для Caddy или `http://spotify:8080` для nginx. Одной публикации порта приложения на loopback хоста для связи контейнеров недостаточно. Данные сертификатов прокси сохраняйте отдельно от `spotify-data`.

Запускайте ровно один Uvicorn worker и одну реплику. Опрос Spotify, подписчики SSE, лимиты попыток входа и кэш текста песен хранятся в памяти процесса.

## Проверка развёртывания

Выполните на сервере (в Windows PowerShell используйте `curl.exe`):

```sh
docker compose ps
docker compose logs --tail 50 spotify
curl --fail http://127.0.0.1:8080/healthz
curl --fail https://music.example.com/healthz
curl --fail https://music.example.com/setup
curl --fail https://music.example.com/widget
curl --fail https://music.example.com/api/v1/spotify/public/currently-playing
curl --fail --no-buffer --max-time 25 https://music.example.com/api/v1/spotify/public/stream
```

Health должен вернуть `{"status":"ok"}`, страницы — HTML. Возьмите настоящий `/assets/...js` из HTML страницы и запросите его отдельно: должен вернуться JavaScript, а не страница ошибки. В SSE сразу должны появиться `retry: 5000` и `event: playing`. Последняя команда намеренно завершается по тайм-ауту с кодом curl 28 через 25 секунд: поток остаётся открытым. Не используйте `-k`: браузер тоже должен доверять сертификату.

Если установлен Python 3.13+, можно выполнить ту же проверку, которую использует CI. Она требует только стандартную библиотеку Python и не запрашивает пароль владельца:

```sh
python scripts/check_deployment.py https://music.example.com
```

Скрипт дожидается health, проверяет обе страницы и их JS/CSS, читает playback JSON и первое событие SSE, затем завершается. Для локальной проверки можно указать `http://127.0.0.1:8080`.

До подключения Spotify пустое состояние воспроизведения нормально. Завершите вход через браузер и включите поддерживаемый трек, чтобы проверить реальный доступ к Spotify. Затем проверьте виджет на HTTPS-сайте или в OBS. CI собирает образ и проверяет запуск контейнера, health, страницы, собранные ассеты, playback JSON и SSE с тестовой конфигурацией. Публичный DNS, выпуск сертификатов и реальные аккаунты провайдеров CI не проверяет.

| Симптом | Что проверить |
| --- | --- |
| Контейнер завершается при старте | Обязательные значения `.env`, ключ шифрования, права каталога данных и журнал контейнера |
| `502 Bad Gateway` | Локальный `/healthz`, upstream и расположение прокси: хост или контейнер |
| Сертификат не выпускается | DNS, устаревшие AAAA-записи, входящие порты и другие службы на 80/443 |
| Ошибка state при входе | Начните заново с того же публичного HTTPS `/setup`; домен callback и cookie должны совпадать |
| Обновления приходят пачками | Буферизация, сжатие и кэширование SSE на каждом прокси/CDN |
| Страница работает, iframe заблокирован | Mixed content, заголовки встраивания прокси и `frame-src` родительского сайта |

## Обновление

В каталоге с настроенным `.env` и Compose-файлом выполните:

```sh
git pull
docker compose up --build -d
```

Сохраните прежние `.env` и имя Compose-проекта, чтобы приложение использовало исходный ключ шифрования и том данных. Если исходники получены архивом, обновляйте их с сохранением `.env`.

## Данные и резервные копии

В томе `spotify-data` хранится зашифрованное состояние SQLite, включая Spotify-токены и ID Telegram-сообщения. Контейнер работает от UID/GID 10001. При использовании собственного bind mount дайте этому пользователю право записи.

Делайте резервную копию тома вместе с соответствующим `.env`. Перед копированием базы остановите приложение, чтобы файлы SQLite и её журнала были согласованы. Храните копии в закрытом доступе: `.env` содержит ключ расшифровки.

- `docker compose down` сохраняет том данных.
- `docker compose down -v` удаляет том и его содержимое.
- Замена `ADMIN_KEY` меняет только пароль настройки.
- При потере `TOKEN_ENCRYPTION_KEY` сохранённое состояние нельзя расшифровать.

При потере ключа сначала восстановите исходное значение из резервной копии. Если его нет, создайте новую базу и ключ, затем подключите Spotify заново. В новой базе также не будет старого ID Telegram-сообщения, поэтому публикация начнётся с нового сообщения.

## Журналы и доступность

В команде Uvicorn отключены access logs. На прокси исключите или очистите query string `/auth/callback`, чтобы коды авторизации и state не попадали в журналы. Не включайте HTTP debug logs с рабочими ключами.

```sh
docker compose ps
docker compose logs --tail 50 spotify
curl http://127.0.0.1:8080/healthz
```

Health check проверяет, что приложение отвечает на запросы. Доступность Spotify, Telegram и провайдера текста проверяется отдельно. Ошибки внешних сервисов описаны в [разделе решения проблем](configuration.ru.md#решение-проблем).

## Публичное воспроизведение

Виджет и playback endpoints публичны. Посетителям доступны текущий трек, позиция, пауза, обложка и включённый текст песни. Пароль владельца страницы `/setup` храните в закрытом доступе. Чтобы прекратить показ, отключите Spotify через `/setup` или остановите приложение.
